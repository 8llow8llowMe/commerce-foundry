# USD 고정 가격 정책과 후속 구현 계획 (#20 A)

## 1. 적용 범위와 현재 상태

이 문서는 관리자 수동 고정 KRW/USD 가격 정책의 정본이다. 환율 환산은 도입하지 않는다.
**A는 정책·명세 문서만 확정한다. B~E의 코드·DDL·설정·운영 적용은 별도 승인 대상이다.**
가격행을 사용하는 서비스 흐름, 명시 통화 조회, 통화 미지원 SKU의 nullable 가격은 아직 구현되지 않은 목표 계약이다.
이 문서가 작성됐다고 신규 명시 통화 USD 표시·주문·결제가 활성화되거나 기존 API가 바뀌지 않는다.

| 구분 | 현재 구현 | 확정된 목표 정책 |
|---|---|---|
| 상품·SKU 가격 | 상품별 단일 통화, 기존 USD 상품도 가능 | 상품×통화 기본가·정가, SKU×통화 추가금 |
| internal SKU 조회 | 통화 없는 조회, 금액 필수인 기존 모델 | 별도 명시 통화 계약과 호환 adapter |
| 주문 통화 | 조회한 SKU에서 추론 | 명시 통화 선택과 기존 미지정 동작 병행 |
| 결제 | KRW만 허용 | E 검증·개방 승인 후 USD 지원 |
| 고객 통화 선택 | 새 선택 계약 미구현 | 언어와 독립적인 명시 통화 선택 |

기존 단일 통화 금액을 KRW라고 가정하지 않는다. 실제 DB의 통화 분포·가격값은 확인하지 않았다.
기존 기준통화, 통화 미지정 요청의 선택 의미·응답, v1 주문 지문은 영구 호환 대상이다.
이 문서의 논리적인 가격행 이름은 실제 테이블명이나 API 필드명을 확정하지 않는다.
정확한 테이블·인덱스·경로·필드·오류 코드는 B/C/D 구현 명세 승인 때 정한다.
A에서는 실행 SQL·DDL, 기능 플래그명, 운영 가격값, 운영 이행 창을 만들지 않는다.

### B1a 저장 기반의 구현 범위

B1a는 `product_price`·`sku_price` 엔티티와 가격 값/집합, passive 벌크 저장·조회 Port/Adapter를 추가한다.
기존 서비스의 가격 읽기·쓰기 caller에는 연결하지 않는다. 신규 테이블이 비어 있어도 기존 API는 기존 컬럼을 사용한다.
쓰기 adapter는 호출자 트랜잭션을 요구하지만 부모 상품 CAS 연결·구 writer 동기화·backfill·정본 전환은 후속 B1b/B1c 범위다.
따라서 저장 기반 추가가 기준통화 집합의 실제 DB 완전성이나 USD 판매 지원 완료를 보장하지 않는다.
`PriceBook`은 전체 legacy SKU 상태와 가격행을 명시 입력받아 불변식을 검증하며 재고를 필터하지 않는다.
추가 통화 지원 SKU 0개 상태의 허용 여부는 B2 합의 대상이라 B1a에서 새 거절 정책을 확정하지 않는다.
구 스키마 확장 테스트는 동결한 product/sku 두 테이블의 모든 컬럼값·구조 보존과 관련 네 매핑만 검증한다.
나머지 서비스 스키마 검증은 전체 생성 스냅숏과 모듈 검증으로 구분하며 실제 운영 이행 완료를 뜻하지 않는다.

### B1b A 미연결 가격 조율기의 구현 범위

B1b A에서 `LegacyPriceSnapshot`·`LegacyPriceWritePlan`·`LegacyPriceWriteProcessor`의 caller 없는 준비·쓰기 조율기를 추가한다.
기준통화 누락행 보완, 기존 가격 drift·추가 통화 불변식 검사와 기준통화 금액 변경 계획을 담당한다. 세 Processor 메서드는 호출자 트랜잭션을 요구한다.
B1b B는 기존 다섯 writer를 같은 트랜잭션의 부모 CAS/@Version 보호 아래 연결한다. 실제 변경 시 기준통화 누락행을 보완하고 추가 통화 불변식을 검사한다.
가격 동일값·기은퇴 no-op은 가격행을 조회하거나 보완하지 않는다. backfill·정본 전환·운영 검증은 미완료이며 신규 USD 구매는 활성화하지 않는다.

## 2. 가격 모델과 불변식

가격은 product-service의 기존 상품 컨텍스트가 소유한다. 별도 가격 서비스를 만들지 않는다.
상품·옵션·SKU 식별자, 재고, 선점, 장바구니를 통화별로 복제하지 않는다.
논리 키 `(productId, currency)`, `(skuId, currency)`는 각각 유일해야 한다.
기존 원시 ID와 Port/Adapter 경계를 유지하고 JPA 연관관계를 도입하지 않는다.
가격 조회는 벌크로 처리하며 루프 안 단건 조회로 N+1을 만들지 않는다.

| 논리 단위 | 저장할 값 | 관계 |
|---|---|---|
| 상품×통화 | 기본 판매가, 선택 정가 | 해당 통화 SKU 가격의 부모 |
| SKU×통화 | 추가금 | 같은 상품·같은 통화 기본가에 가산 |

- SKU 판매가 = 같은 통화 상품 기본 판매가 + SKU 추가금이다.
- 금액은 `long` 최소 화폐 단위다. KRW는 소수 0자리, USD는 2자리(센트)다.
- 기존 `CurrencyCode`, `Money`, PG adapter의 `BigDecimal` 주단위 변환을 재사용한다.
- `double`·`float`를 쓰거나 서비스마다 센트 변환을 중복 구현하지 않는다.
- 추가금은 0 이상이다. 정가가 있으면 기본 판매가와 통화가 같고 기본 판매가보다 커야 한다.
- 통화별 가격 지원 `ON_SALE` SKU가 있으면 그 집합에 추가금 0인 SKU가 하나 이상 있어야 한다.
- 모두 판매 중지 상태이면 이 zero 조건은 적용하지 않는다.
- 이 집합은 재고 품절 SKU도 포함한다. 재고 변화만으로 기본가 불변식을 바꾸지 않는다.
- 부분 SKU 지원은 추가 통화에서만 허용한다. 추가 통화를 지원해도 모든 SKU에 그 통화 가격을 강제하지 않는다.
- 추가 통화 미입력 SKU 가격은 null이며 해당 통화 구매 선택이 불가능하다. 실제 금액 0과 구분한다.
- 상품 기본 가격 없이 SKU 추가금만 남는 휴면 가격은 허용하지 않는다.

통화 지원 여부, 판매 상태, 재고 품절은 서로 다른 판정이다.
USD 가격 미입력 SKU를 품절로 취급하거나 0원으로 표시하지 않는다.
0원 판매 허용 여부와 PG 최소 결제 금액은 별도 구매 검증이며, null을 0으로 바꿀 이유가 되지 않는다.

### 2-1. 기준통화와 삭제

기준통화는 기존 계약대로 불변이다. 기준통화 가격행은 삭제하지 않는다.
기존 USD 기준 상품에도 같은 규칙을 적용하며 KRW로 강제 전환하지 않는다.
판매 중지·은퇴를 포함해 legacy 경로에 노출되는 모든 SKU에는 상품과 같은 기준통화 추가금행이 필수다.
기준통화 SKU 추가금행은 삭제하거나 요청에서 누락해 없앨 수 없다. 기존 금액 필수 응답을 영구 보존한다.
신규 SKU 생성도 같은 DB 트랜잭션·부모 CAS 안에서 기준통화 추가금행을 반드시 만든다.
추가 통화만 삭제할 수 있고, 그 상품의 해당 통화 SKU 가격 집합까지 같은 트랜잭션에서 삭제한다.
상품 가격만 삭제해 자식 SKU 금액이 남거나 SKU만 별도로 복구되는 상태를 만들지 않는다.
구체적인 요청 형식과 삭제 오류 코드는 B2 명세에서 확정한다.
추가 통화 상품 가격행은 있지만 그 통화 지원 SKU가 전혀 없는 상태의 허용 여부는
B2 진입 명세에서 합의할 세부 조건이며 A에서 임의 확정하지 않는다.

### 2-2. 원자 편집과 경쟁

상품 가격과 해당 통화 SKU 추가금 집합은 같은 DB 트랜잭션·부모 상품 version CAS로 저장한다.
요청 SKU 집합이 실제 상품 소속인지, 중복·누락·잘못된 membership이 없는지 검증한다.
자식 저장·삭제, 불변식, CAS 중 하나라도 실패하면 전체 가격 편집을 롤백한다.
중간 상태의 기본가나 zero SKU만 먼저 외부에 보이게 저장하지 않는다.

판매 상태 변경, 옵션 은퇴, 새 SKU 추가가 통화별 가격 지원 `ON_SALE` 집합을 바꾸면
변경 후 모든 통화의 zero SKU 불변식을 같은 경쟁 제어 아래 다시 검증한다.
기존 가격·SKU 편집 요청에 추가 통화 필드가 없다는 이유로 추가 통화 가격을 지우지 않는다.
기존 API의 no-op과 버전 증가 의미는 현재 계약을 유지하면서 별도 호환 테스트로 고정한다.
ADMIN 인가와 감사 원칙을 유지하고 가격 원문을 감사 로그에 추가하지 않는다.

## 3. 언어·통화 선택과 고객 계약

`Accept-Language`는 문구를 고른다. 명시 통화는 가격을 고른다.
`en`이 USD를 자동 선택하지 않으며 `ko+USD`, `en+KRW` 조합도 가능하다.
영문 스토어 기본 USD가 필요하면 FE/BFF가 명시 통화를 전달하는 계약으로 구현한다.
통화 미지정 요청은 현재의 선택 의미와 응답을 보존한다. 이를 KRW 기본값으로 재정의하지 않는다.
명시 통화 없음과 명시 KRW가 동일하다는 가정을 캐시나 주문 지문에 넣지 않는다.

| 명시 통화 요청 | 목표 동작 |
|---|---|
| 지원하지 않는 통화 값 | 400, 다른 통화나 환산으로 대체하지 않음 |
| enum은 지원하지만 상품 가격 미등록 | 목록에서 제외, 해당 통화 상품 상세는 404 |
| 추가 통화 상품 가격 등록, 일부 SKU 미등록 | 상세에서 기존 SKU ID·옵션 조합 유지, 미지원 상태와 가격 null |
| 가격 등록 SKU의 재고 품절 | 가격 유지, 품절 상태로 구분 |

목록 통화 필터는 DB 페이지 조회 전에 적용한다. 메모리에서 페이지 결과를 뒤늦게 거르지 않는다.
가격 정렬과 표시 기본가·할인율도 선택 통화의 가격을 사용한다.
상품 목록, 상세, 전시 카드, Look 카드가 같은 통화 지원 판정을 사용해야 한다.
가격 미등록 SKU의 옵션 조합을 삭제하거나 KRW 가격·0으로 대체하지 않는다.
`NOT_SOLD_IN_CURRENCY`는 후속 구현에서 표현할 예정인 의미이며 현재 오류 코드나 응답 필드가 아니다.

장바구니는 미지원 줄을 보존하고 합계에서 제외하며, 통화 변경 후 선택 불가 사유를 보여준다.
줄을 자동 삭제하거나 통화마다 장바구니를 따로 만들지 않는다.
정확한 줄 상태·nullable 필드·합계 계약은 C/D와 FE 검토에서 확정한다.

고객 상품·전시·Look·BFF/CDN 캐시는 언어와 명시 통화 차이를 구별해야 한다.
명시 통화 누락 요청도 별도 의미로 보존하며, 쿼리 누락으로 다른 통화 결과가 섞이지 않게 검증한다.
헤더를 쓰는 최종 계약이면 해당 헤더의 캐시 키와 `Vary`도 검증한다.

### 3-1. internal 호환 경계

현재 통화 없는 internal SKU 조회와 금액 필수 모델을 그대로 nullable로 바꾸지 않는다.
새 명시 통화 계약·모델과 기존 호출자를 위한 호환 adapter를 따로 설계한다.
새 계약의 bulk 조회도 루프 안 단건 호출 없이 처리하며 기존 인증·허용 호출자를 유지한다.
기존 `CatalogSku` 금액 필수 경로에 통화 미지원 null 응답을 밀어 넣지 않는다.
새 필드와 오류 코드는 구현 명세에서 확정하고 구·신 호출자의 혼합 배포를 검증한다.

## 4. 저장 이행과 정본 전환

다음 순서가 유일한 이행 원칙이다. 서로 독립된 두 정본이나 비동기 dual write는 허용하지 않는다.
실제 운영 DB 분포·중단 가능 시간·배포 창은 미확인이고, 실행 계획은 B1에서 별도 승인한다.

1. 초기에는 기존 가격 컬럼이 정본이다. 모든 가격 writer와 판매 가능 SKU 집합 변경을 식별한다.
   호환 writer는 기존 컬럼과 신규 가격행을 같은 DB 트랜잭션·부모 CAS 안에서 동기화한다.
   이 전환기에는 기존 필드가 읽기 정본이며 신규 가격행을 독립적인 읽기 정본으로 취급하지 않는다.
2. 기존 행의 실제 currency를 그대로 사용해 backfill한다. KRW 가정이나 환율 환산은 하지 않는다.
   스냅숏 뒤 발생한 편집을 구값으로 덮지 않도록 version fence·재시도·중단 재개를 설계한다.
3. 모든 writer의 호환 배포와 구·신 대조가 완료된 후 가격행을 단일 정본으로 전환한다.
   일부 writer가 기존 컬럼만 쓰는 상태에서 정본을 먼저 전환하지 않는다.
   전환 완료 후 읽기·쓰기 정본은 가격행 하나이며 기존 필드는 호환 투영이다.
4. 전환 뒤에도 legacy 기준통화 포인터를 보존하고 가격행에서 기존 응답으로 투영하는 기능을 영구 지원한다.
   통화 미지정 호출의 의미, 기존 USD 상품, v1 주문 지문을 유지한다.

가격 0, 정가 null, 기존 KRW·USD 데이터를 손실 없이 보존해야 한다.
사전 점검에서 구데이터의 상품/SKU 통화 불일치·참조 누락이 발견되면 이행을 차단한다.
임의로 통화를 추정하거나 0원으로 보정하지 않고 데이터 원인과 복구 방식을 별도 확인한다.
재실행 가능함은 최신 편집까지 덮어써도 된다는 뜻이 아니다.
정본 전환 전후 경합·행 누락·불변식 위반을 대조하고 미해결 차이가 있으면 전환을 멈춘다.

### 4-1. 롤백 순서

1. 신규 기능을 OFF로 유지하거나 끄고 신규 유입을 중단한다.
2. 새 통화 가격행과 기존 가격·버전 정보를 보존한다. 신규 가격을 삭제해 구모델에 맞추지 않는다.
3. 신규 가격과 부모 CAS를 이해하는 호환 writer로만 복귀한다.
4. 정본·투영·writer 대조 후 재개 여부를 결정한다. 신규 가격을 모르는 구 binary로 복귀하지 않는다.

실행용 DDL과 적용·복구 순서는 B1의 별도 산출물이다. A에는 SQL을 포함하지 않는다.
이행을 실제 PostgreSQL에서 검증하기 전에는 운영 적용 가능 또는 무중단 완료라고 보고하지 않는다.

## 5. 주문 계산·멱등성과 구매 gate

preview와 create는 동일한 서버 가격 선택·계산 규칙을 사용한다.
`expectedTotalAmount`는 계산 결과 대조값이며 통화나 가격표를 선택하는 입력이 아니다.
과거 주문·배송·결제·환불은 저장된 스냅숏과 원승인 통화·금액을 사용한다.
현재 상품 가격이나 환율로 과거 거래를 재계산하지 않는다.

### 5-1. 주문 지문

- 통화 미지정 legacy 요청은 기존 v1 canonical 입력 바이트와 결과를 영구 보존한다.
- 미지정 v1에 기본 KRW나 새 버전 문구를 추가하지 않는다.
- 명시 통화 요청만 새 버전 canonical 입력에 통화를 포함한다.
- 저장 지문은 기존과 같은 64자리 hex SHA-256이다. 저장값에 `v2:` 접두사를 붙이지 않는다.
- 같은 멱등 키에서 명시 통화를 바꾸면 다른 본문 충돌로 거절한다.
- 완료 요청 재생은 원격 가격·배송 조회와 신규 구매 gate보다 먼저 저장 결과를 반환한다.

legacy 혼합 통화 장바구니에서 `Money.plus`가 500을 일으킬 가능성은 기존 잠재 결함이다.
500을 영구 호환 계약으로 보존하지 않으며 D에서 명시적인 오류 정책과 테스트를 정의한다.

### 5-2. USD 신규 구매 차단과 개방

D/E 검증·개방 승인 전에는 최종 유효 통화가 USD인 신규 구매를 OFF로 유지해야 한다.
명시 USD뿐 아니라 통화 미지정 요청에서 SKU로 추론된 USD도 차단 대상이다.
신규 요청 기록, lease 인수 갱신, 주문 생성, 재고 선점보다 먼저 차단해야 한다.
완료 재생은 앞서 반환하며, 기존 요청 기록·선점을 자동 삭제하거나 해제하지 않는다.
정확한 gate 소유 서비스·설정·거절 계약은 D 명세에서 정하고 기존 복구 gate를 재사용하지 않는다.

**A는 이 차단을 구현하지 않는다. 현재 KRW 결제 제한만으로 주문·선점 전 차단이 보장되지 않는다.**
후속 gate의 실제 실행 순서와 미지정 USD 차단을 입증하기 전에는 신규 명시 통화 USD 기능을 노출·활성화할 수 없다.
기존 legacy USD 응답의 영구 호환과 새 기능 개방은 구분한다.
관리자 USD 가격 등록과 고객 USD checkout 개방은 서로 다른 완료 기준이다.

## 6. 배송·PG와 보호할 복구 계약

배송비 정책과 주문 통화가 다르면 기존대로 거절한다. 환산 또는 무료 배송으로 대체하지 않는다.
USD 상품 등록이 국내 KRW 배송 정책으로 checkout할 수 있다는 뜻은 아니다.
실제 USD 배송 정책, 배송 국가, 무게·HS 정보와 운영 이행 창은 확인하지 않았다.

토스 공식 해외결제 가이드는 PayPal USD, 추가 계약, 통화별 MID 구성과 상품·배송 정보 연동을 안내한다.
이는 실제 고객사의 추가 계약·MID·키가 준비됐다는 증거가 아니다.
[토스 해외결제 가이드](https://docs.tosspayments.com/guides/v2/learn/foreign-payment)

USD 승인·취소·조회에는 원승인 통화와 정확한 소수 변환을 적용해야 한다.
취소 요청 `currency`, 원승인 `totalAmount`, 취소 가능 잔액 `balanceAmount`를 구분한다.
부분 취소 뒤 잔액을 원승인 gross 금액으로 덮지 않는다.
[토스 코어 API](https://docs.tosspayments.com/reference)

#308 C3의 후속 소비·복구는 별도 범위이며 기존 gate를 유지한다.
[최초 결제 반영 결과 조회 계약](order-payment-result-guide.md)을 함께 따른다.
엄격한 order-result 7필드, 문자열 ID, 정수 amount/currency의 Money 계약을 보존한다.
`REJECTED_PAYMENT_NOT_DONE`의 `stockReservationId`는 null이며, 원 `approvedAt`과 최초 reason, inbox 멱등성을 유지한다.
결과 조회 성공은 회신 ACK 반영·주문 동기화·PG 취소 완료가 아니다.
USD 가격 정책만으로 회신·취소·복구 gate를 변경하거나 켜지 않는다.

## 7. A~E 단계와 승인 경계

| 단계 | 산출물·완료 기준 | 개방 상태 |
|---|---|---|
| A 정책·명세 | 이 문서와 기존 문서 링크, 현재/목표 구분, 단계별 계획 | 문서만 승인, 구현 없음 |
| B1 저장·이행 | 가격행, 모든 구 writer 호환, 정본 전환·복구 검증 | 신규 명시 통화 USD 미개방 |
| B2 관리자 편집 | 통화별 원자 편집·삭제, 부분 SKU·zero·인가·감사 | 신규 명시 통화 USD 미개방 |
| C 고객·internal | 명시 통화, 목록·상세·카드·정렬·캐시, 호환 모델 | gate 실증 전 신규 명시 USD 기능 노출 불가 |
| D cart·order | 합계·지문·스냅숏·신규 gate·완료 재생 | E 개방 승인 전 USD 구매 OFF |
| E 결제·배송·FE | USD PG 전 경로·배송·#308 C3·FE 계약과 운영 준비 검증 | 별도 개방 승인 필요 |

B1/B2만 끝나도 통화 판매 지원이나 #20 전체 완료가 아니다.
후속 소스·DDL은 각 구현 명세와 범위를 승인받은 뒤 작업한다.
PR은 30파일·1,000줄 이내를 목표로 하며 초과 예상 시 완결 가능한 단위로 분할한다.

### 7-1. B1 저장·구 writer 호환·이행 상세 계획

예상 영향은 `product-service` 가격 도메인·영속성·기존 등록/가격/SKU/옵션 writer와 그 테스트다.
공용 `Money`/`CurrencyCode`는 재사용하며 공용 모듈 변경은 필요성이 확인될 때 별도 범위로 잡는다.
order/payment/delivery 코드나 운영 플래그를 B1에 끌어오지 않는다.

1. 실제 writer 목록과 부모 버전 경쟁 경계를 조사하고 이행 단계별 읽기·쓰기 정본을 명세한다.
2. 논리 가격행의 제약·인덱스와 기존 컬럼 투영을 설계한다. 실제 스키마·DDL은 별도 승인한다.
3. 기존 모든 writer를 같은 DB 트랜잭션·CAS로 동기화하고 기존 요청/응답을 보존한다.
4. 실제 currency 그대로 backfill하고 version fence·재시도·중단 재개·대조 절차를 구현한다.
5. 모든 writer 호환과 대조 완료 후에만 가격행 정본 전환을 검증한다.

완료 기준은 신규 KRW뿐 아니라 기존 단일 USD 상품의 금액·기준통화·응답이 보존되는 것이다.
판매 중지·은퇴 SKU의 기준통화 추가금행과 신규 SKU 생성의 같은 TX/CAS 보장을 검증한다.
기준통화 자식행 누락·삭제 거절, 구데이터 통화 불일치·참조 누락 사전 차단도 필수다.
가격 0·정가 null, 재실행·경합·중단·롤백, 자식 쓰기 실패의 전체 롤백을 포함한다.
판매 상태·은퇴·SKU 추가도 모든 통화 불변식을 우회하지 않아야 한다.
v1 미지정 주문 지문 fixture를 원본 canonical 바이트와 64자리 결과로 고정해 가격 이행의 호환 근거로 남긴다.

검증은 단위 불변식, 실제 PostgreSQL 질의·제약·CAS, 구 스키마에서 업그레이드하는 통합 시나리오 순서다.
구 KRW/USD 혼합 fixture와 동시 편집을 사용하고 H2나 새 스키마 생성만으로 이행을 검증했다고 하지 않는다.
바뀐 서비스의 `cleanTest`·`check --no-build-cache`를 실행하고 공용 변경 시 전 모듈 컴파일도 한다.
롤백 리허설은 신규 기능 OFF → 신규 가격 보존 → 호환 writer 복귀 → 정본/투영 대조 순서다.
실제 DB 대조와 복구 증거가 없으면 B1을 운영 적용 완료로 표시하지 않는다.

### 7-2. B2 관리자 통화별 편집 상세 계획

예상 영향은 `product-service` ADMIN Controller·DTO·UseCase·Facade·Processor·Presenter·Port·Adapter다.
기존 가격/SKU/옵션 변경 경로와 인가·감사·API 문서·FE 편집 화면 계약도 검토 범위다.
고객·어드민·internal DTO를 공유하지 않고 식별자 문자열 변환은 Presenter에서 한다.

1. 상품 기본가·정가와 해당 통화 SKU 집합을 함께 보내는 원자 편집·삭제 계약을 명세한다.
2. 추가 통화의 부분 SKU 지원과 미입력/실제 0, 기준통화 삭제 금지, 추가 통화 원자 삭제를 구현한다.
3. membership·부모 CAS·zero SKU를 검증하고 판매 상태/은퇴/새 SKU 경합을 함께 다룬다.
4. 기존 FE payload에서 빠진 추가 통화를 보존하고 기존 no-op/버전 의미를 회귀 검증한다.
5. ADMIN 권한·감사와 한국어 Swagger, 오류 코드, FE 호환 판단을 문서화한다.

완료 기준은 유효 편집만 전체 저장되고 충돌·membership 오류·불변식 위반은 전체 롤백되는 것이다.
기준 USD 상품도 삭제 금지 규칙이 같고 추가 통화 삭제 후 자식 가격이 남지 않아야 한다.
판매 중지·은퇴를 포함한 모든 legacy SKU 기준통화 추가금행의 삭제·누락 거절을 검증한다.
신규 SKU 생성 시 기준통화 자식행을 같은 TX/CAS로 저장하고 기존 금액 필수 응답이 유지돼야 한다.
재고 품절 zero SKU를 포함하는 집합 검증과 추가금 0 SKU를 없애는 상태 경쟁 테스트가 필요하다.
인가 스모크·컨텍스트 로딩·실제 PostgreSQL CAS·기존 FE payload 회귀를 실행한다.
API 계약은 `seonghoho` FE 리뷰와 계층·DB·보안·결제/주문·최종 검토를 받는다.
롤백은 편집 기능 OFF → 신규 가격 보존 → B1 호환 writer 유지 → 구 응답 투영 대조 순서다.
통화를 모르는 구 binary로 관리자 편집만 되돌려 신규 가격을 지우는 복귀는 금지한다.

### 7-3. C·D·E 후속 완료 기준

C는 product 고객·internal 및 FE/BFF 계약에 영향을 준다. 언어×통화 조합, 누락 요청,
미등록/null/실제 0/품절, 필터 후 페이지·선택 통화 정렬, 전시·Look·캐시와 bulk N+1을 검증한다.
기존 금액 필수 internal 호출자와 새 모델의 혼합 배포·호환 adapter 테스트가 완료돼야 한다.

D는 order의 cart·preview/create·요청 기록·선점 연동에 영향을 준다.
v1 바이트·재생, 새 canonical 64hex, 같은 키의 통화 충돌, 과거 스냅숏을 검증한다.
명시/미지정 USD 신규 요청의 기록·lease 인수 갱신·주문·선점 전 차단과
완료 재생의 원격 조회·gate 우선 반환을 장애 주입으로 입증한다. 기존 기록·선점은 보존한다.

E는 별도 소유의 payment·delivery와 FE 통합 단계다. 실제 계약/MID/키·배송 정책을 확인하고
승인·취소·부분 환불·재조회·UNKNOWN·웹훅·재선점·회신 중복·복원 경로를 원승인 통화로 검증한다.
#308 C3 계약과 gross/잔액, 최초 시각·사유·inbox 멱등성을 보존해야 한다.
가격 화면 완료만으로 E를 완료 처리하지 않으며 운영 준비와 별도 개방 승인 뒤에만 신규 명시 통화 USD 기능을 연다.
