## 설계 대조 결과와 미해결 사항

메인과 읽기 전용 architect·DB 역할이 최신 코드를 대조했다. 두 사전 검토의 확정 C/H는 각각 0/0이나 구현 완료 검토가 아니다. dev-orchestrator·pr·payment-guard·order-flow-guard를 확인했고 실제 구현 guard·전문/최종 리뷰는 아직 미완이다.

- 원천은 최초 저장 스냅숏이며 이벤트는 알림이다. 이벤트와 원천의 payment/order/종류/거절 코드를 먼저 대조한다. PAID 원천과 거절 이벤트 불일치는 영구 실패이며 늦은 거절 no-op으로 삼키지 않는다.
- 원천 DTO 생성자 자체는 필드 검증을 하지 않으므로 C3b에서도 null/result/amount·양수 ID·PAID 시각/선점 ID와 거절별 선점 ID 규칙을 재검증해야 한다.
- 원천/로컬은 order/member/원승인 총액·통화/마이크로초 승인 시각을 대조한다. 거절 시각 null은 허용하며 주문 처리 시각 paidAt와 PG approvedAt를 혼동하지 않는다.
- 정상 DONE 기원 DONE/PARTIAL_CANCELED/CANCELED만 허용한다. 늦은 승인 기원은 거절하고 성공 단조성을 유지한다.
- payment saveAndFlush 성공 뒤 inbox INSERT는 커밋 때 실패할 수 있다. 프록시 밖 경계에서 래핑된 commit/version/정확한 inbox unique와 기타 제약의 분류를 추가 검토해야 한다. 원문·ID·cause·임의 태그를 전파하지 않는다.
- inbox 최종 방어는 `uk_processed_event_consumer_group_event_id`다. 실패한 TX 안에서 재조회하지 않고 새 진입으로 판정한다. no-op은 payment 저장·버전 검사를 생략한다.
- 실제 취소 complete는 행 잠금 후 최신 payment를 재조회한다. 취소 선행이면 회신 stale CAS 실패를, 회신 선행이면 취소가 sync 필드를 보존함을 검증한다. 양쪽 모두 VERSION 충돌을 기대하거나 잠금 뒤 양자 barrier를 두면 안 된다.
