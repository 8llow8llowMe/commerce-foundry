# Development Orchestrator

## Codex · Cursor 실행 방식

- 역할 지침 원문은 저장소 루트 기준 `.agents/roles/<역할>.md`다. 네이티브 하위 에이전트로는
  Cursor `.cursor/agents/`(전 역할)와 Codex `.codex/agents/`(`explorer`·`git_ops`)가 생성돼 있다.
- 하위 에이전트를 사용할 수 있고 위임이 허용된 경우에만 역할 지침·범위·기대 출력을 전달해 위임한다.
  그 외에는 메인 세션이 동일한 역할을 순차 수행하고, 실제 수행 방식을 보고한다.
- 읽기 전용 역할은 소스·설정·문서를 편집하지 않는다. 실행 도구의 권한 제한을 적용할 수 있으면 함께 적용한다.
  검사 명령은 빌드 산출물을 만들 수 있지만, 파괴적인 셸 명령과 외부 변경은 허용되지 않는다.
- 쓰기는 한 번에 한 역할만 수행한다. 하위 에이전트의 모델·읽기 전용 여부는 생성된 정의를 따른다.
- 범위 밖 이슈 등록·커밋·푸시·PR·머지는 실행하지 않는다. FE 작업은 `fe-implementer`와 `fe-reviewer`를 선택한다.

메인 세션이 작업 유형과 복잡도를 정한 뒤, 필요한 역할만 실행한다.
역할 적용·실행·권한 안내는 [docs/ai-agents.md](../../../docs/ai-agents.md) 다.

## 모델 라우팅

토큰은 "누가 얼마나 읽느냐" 에서 가장 많이 든다. 메인 세션은 판단에 쓰고, 많이 읽거나 기계적으로 반복하는 일은 저비용 모델 역할로 내린다.

| 일 | 맡는 곳 |
|----|---------|
| 분류·계획·범위 결정, 검증 실행·결과 확인, 완료 판단 | 메인 세션 |
| 위치·호출 흐름을 모르는 탐색, 여러 파일 훑기 | `explorer` (저비용 모델) |
| 이슈 시작·푸시·PR 생성·머지 후 정리 같은 git·gh 작업 | `git-ops` (Codex `git_ops`, 저비용 모델) |
| 설계·구현·검토 | 해당 역할 (현재 세션 모델) |

- 저비용 모델은 `.codex/agents/`·`.cursor/agents/` 정의에 있다. 위임할 수 없으면 메인 세션이 같은 순서로 처리한다.
- 위치를 아는 파일 몇 개 읽기, 단일 git 명령은 메인 세션이 직접 한다. 하위 에이전트는 새 컨텍스트로 시작하므로 띄우는 비용이 더 크다.
- 하위 에이전트는 대화 기록을 보지 못한다. 경로·브랜치·이슈 번호·검증 결과·원하는 출력 형식을 전달한다.
- 결과는 요약으로 받는다. diff·파일 원문을 통째로 돌려받지 않는다.

## 1. CLASSIFY

| 유형 | 대상 |
|------|------|
| `SIMPLE` | 위치와 계약이 분명한 DTO, 매핑, 단순 검증·설정, 작은 테스트, 문구 |
| `FEATURE` | 일반적인 단일 서비스 기능 |
| `BUG` | 원인 분석이 필요한 버그. 상태·트랜잭션·동시성이 얽히면 여기 |
| `REFACTOR` | 동작을 보존하면서 구조를 바꾸는 변경 |
| `ARCHITECTURE` | 서비스 경계·서비스 간 정합성·보안·메시징 설계 |
| `LARGE_FEATURE` | 여러 서비스(또는 BE+FE)에 걸쳐 발견 역할이 둘 이상 필요한 작업 |

## 2. COMPLEXITY

| 등급 | 의미 | 기본 깊이 |
|------|------|-----------|
| `T0` | 위치·계약·검증이 확정된 국소 변경 | 메인 세션이 직접. 탐색·설계·별도 검토 생략 가능 |
| `T1` | 한 모듈 안의 일반 구현·수정 | 구현 역할 + 대상 테스트 |
| `T2` | 여러 계층, 공개 API, 쿼리·인덱스, 경계 검토가 함께 있는 작업 | 구현 + 검토 역할 1~2 |
| `T3` | 실수 비용이 큰 작업 | 설계 고정 + 구현 + 해당 검토 역할 전부 |

`T3` 는 아래 신호 중 **2개 이상**이 작업 범위에 실제로 있을 때다. 하나뿐이면 `T2` 다.

- **결제 (승인·취소·환불·웹훅)**
- **재고 선점·만료처럼 시간과 동시성이 있는 상태**
- 주문·결제 상태 전이 변경
- 멱등성
- 인증·인가 · 어드민 권한
- 개인정보 (주소·전화번호)
- 서비스 간 정합성 (한쪽만 성공하는 경로)
- DB 스키마 변경 · 대량 데이터 이관
- 공개 API 하위 호환 (FE 계약 변경)
- Gateway·security-core 공통 변경
- 장애 원인 미상

## 3. EXPLORE

- `T0` 이거나 수정 위치가 이미 특정되면 생략한다.
- 위치·호출 흐름이 불명확할 때만 `explorer` 를 부른다. 질문과 찾을 범위(서비스·패키지)를 좁혀서 넘긴다.

## 4. PLAN

- `T0`·`T1` 은 메인 세션이 범위와 순서를 짧게 고정한다.
- `T2` 이상은 구현 전에 범위, 보존할 동작, 검증 방법을 고정한다. 새 컨텍스트면 `/backend-feature-bootstrap`.
- `ARCHITECTURE` 와 `T3` 는 `architect` 의 설계가 저장소 증거와 맞을 때만 구현으로 넘긴다.
- `LARGE_FEATURE` 는 백엔드에 `/backend-multi-agent` 를 적용하고, FE 영향은 별도 작업 단위로 정리한다. FE 이슈 등록·담당자 지정은 요청받은 범위에서만 수행한다.

## 5. IMPLEMENT

| 유형 | 구현 |
|------|------|
| `SIMPLE` | 메인 세션이 직접 |
| `FEATURE` · `BUG`(원인 확정 후) · `REFACTOR` | BE는 `be-executor`, FE는 `fe-implementer` 한 명 |
| `ARCHITECTURE` | 구현 요청이 있을 때만, 확정된 계획을 `be-executor` 에게 |

공유 파일·공개 계약·DB 스키마·도메인 객체를 고치는 쓰기 역할은 **한 번에 하나만** 실행한다.

## 6. VERIFY

대상 범위의 컴파일과 관련 테스트를 **메인 세션이 직접** 돌린다. 하위 에이전트의 "통과했다" 를 완료 근거로 쓰지 않는다.

```bash
cd backend
./gradlew :service:<svc>:cleanTest :service:<svc>:check --no-build-cache   # 바꾼 모듈만(여러 개면 나열)
./gradlew compileTestJava                                                  # core 등 공용 모듈을 바꿨을 때 — 전 모듈 컴파일만
```

- 루트 `./gradlew check`(전 모듈 테스트)는 로컬에서 돌리지 않는다. 다른 모듈은 PR 의 CI(`backend-ci` 그룹 job 건수 표 — 바꾼 모듈과 그 의존 모듈)로 확인한다 — 같은 PC 에서 여러 세션이 빌드한다(`backend/docs/local-run-guide.md` §4-1).
- 데몬을 쓴다. `--no-daemon` 은 JVM 크래시 직후 한 번 다시 돌릴 때만, `./gradlew --stop` 은 쓰지 않는다. 하위 에이전트 프롬프트에도 이 규칙을 넣는다.

FE 변경은 `frontend/`에서 `pnpm lint`, `pnpm format:check`, `pnpm typecheck`, `pnpm test`, `pnpm build`를 실행한다.
문서·AI 설정만 바꾼 경우에는 관련 형식·경로·인코딩 검증을 실행한다.

## 7. REVIEW

| 범위 | 검토 역할 |
|------|-----------|
| 계층·Port/Adapter | `be-hexagonal-reviewer` |
| 엔티티·쿼리·인덱스 | `be-db-reviewer` |
| 인증·인가·어드민·키 | `be-security-reviewer` |
| 결제·주문·재고 | `be-payment-reviewer` |
| 프론트엔드 BFF·쿠키·금액·테마 | `fe-reviewer` |
| 최종 diff 전반 | `reviewer` |

- `T0` 은 대상 테스트로 끝낸다. `T1`·`T2` 는 해당 검토 1~2개, `T3` 는 해당 검토 전부 + `reviewer`.
- 검토 역할은 읽기 전용이라 위임이 허용되고 하위 에이전트를 사용할 수 있으면 **병렬로** 부르고, 그 외에는 메인 세션이 순차 검토한다.
- CRITICAL/HIGH는 해결하고 다시 검증한다. MEDIUM/LOW도 영향과 범위에 따라 수정하거나 남긴 이유를 보고한다.

## 8. SHIP

- 커밋은 메인 세션이 경로를 하나씩 스테이징해 만든다. 커밋이 여러 개이고 경로·메시지가 확정됐으면 `git-ops` 에 넘겨도 된다.
- PR 은 `/pr` 에 **검증 결과를 인자로** 넘겨 만든다.
  예: `/pr 검증: ./gradlew :service:order-service:test 통과 · 참고: payment-guard HIGH 0`
- 머지 후 워크트리·브랜치 정리와 이슈 체크박스 갱신은 PR 번호·완료 항목을 적어 `git-ops` 에 맡긴다.

## 완료 조건

1. 요청한 동작이 구현되었다.
2. 영향 범위가 컴파일되고 관련 테스트가 실제로 돌아 통과했다.
3. 필요한 수준의 검토가 끝났고 CRITICAL/HIGH 지적이 해결되었다.
4. 불필요한 변경과 겹치는 동시 편집이 없다.
5. 보고에 `TYPE`, `COMPLEXITY`(T3 면 해당 신호), 실제 사용한 역할, 실행한 검증, 남은 위험이 있다.
