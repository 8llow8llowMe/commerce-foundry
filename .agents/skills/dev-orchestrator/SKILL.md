# Development Orchestrator

## Codex · Cursor 실행 방식

- 역할 지침 원문은 저장소 루트 기준 `.agents/roles/<역할>.md`다. 네이티브 하위 에이전트로는
  Cursor `.cursor/agents/`와 Codex `.codex/agents/`에 11개 역할이 모두 생성돼 있다.
- Codex에서는 `spawn_agent`에 `agent_type`으로 `.codex/agents/`의 snake_case 이름을 지정한다
  (예: `be_executor`, `be_db_reviewer`). 도구 목록에 이름이 없으면 현재 세션에서 인식되지 않은 것이므로 새 세션에서 확인한다.
- 병렬은 `dev-orchestrator`의 `병렬 실행` 절(네 패턴 · 금지 조건 · 합치기)을 따른다. 한 턴에서 `spawn_agent`를 여러 번 연달아 호출한 뒤 `wait_agent`로 결과를 모은다.
  검토 fan-out 은 영역 리뷰어와 `reviewer`를 같은 턴에 띄운다. 쓰기 병렬은 작업자마다 별도 worktree 를 만들어 그 경로를 지시에 넣는다.
- 하위 에이전트를 사용할 수 있고 위임이 허용된 경우에만 역할 지침·범위·기대 출력을 전달해 위임한다.
  그 외에는 메인 세션이 동일한 역할을 순차 수행하고, 실제 수행 방식을 보고한다.
- 읽기 전용 역할은 소스·설정·문서를 편집하지 않는다. 실행 도구의 권한 제한을 적용할 수 있으면 함께 적용한다.
  검사 명령은 빌드 산출물을 만들 수 있지만, 파괴적인 셸 명령과 외부 변경은 허용되지 않는다.
- 쓰기 병렬의 조건(소유권 분리 · worktree 격리 · 금지 조건 없음)을 모두 만족하지 않으면 쓰기는 한 번에 한 역할만 수행한다.
  Codex 역할은 부모 세션 sandbox 를 상속하므로 읽기 전용은 역할 본문 지시로만 제한된다(Cursor 는 생성된 `readonly`).
- Codex 쓰기 병렬은 작업자 worktree 가 현재 sandbox 쓰기 범위 안일 때만 쓴다. 범위 밖이면 sandbox 를 넓히지 말고 순차로 진행한다.
- 범위 밖 이슈 등록·커밋·푸시·PR·머지는 실행하지 않는다. FE 작업은 `fe-implementer`와 `fe-reviewer`를 선택한다.

메인 세션이 작업 유형과 복잡도를 정한 뒤, 필요한 역할만 실행한다.
역할 적용·실행·권한 안내는 [docs/ai-agents.md](../../../docs/ai-agents.md) 다.

## 모델 라우팅

토큰은 "누가 얼마나 읽느냐" 에서 가장 많이 든다. 메인 세션은 분류·계획·범위 결정·검증 확인·완료 판단에 쓰고,
나머지는 작업 등급에 맞는 모델·추론 수준의 역할로 내린다. Codex 값의 정본은 `.codex/agent-models.json`이다.

| 등급 | 대상 | Codex 모델 | 추론 (기본 → 최대) | 기본 역할 |
|------|------|------------|--------------------|-----------|
| 설계 | 서비스 경계 · 교차 모듈 · 정합성 설계 | `gpt-6.2-astra` | xhigh → ultra | `architect` |
| 핵심 | 치명 버그 · 결제 · 주문 · 재고 · 인증 등 주요 비즈니스 로직의 구현 · 검토 | `gpt-6.2-sol` | high → max | `be_executor` · `fe_implementer` · `be_hexagonal_reviewer` · `be_db_reviewer` · `be_security_reviewer` · `be_payment_reviewer` · `fe_reviewer` · `reviewer` |
| 일반 | CRUD · 매핑 · 단순 화면 등 위험 신호 없는 개발 | `gpt-6.1-terra` | medium → high | 없음 (호출별 지정이 가능한 기본 에이전트 사용) |
| 빠름 | git · gh, 코드 탐색, 대량 반복, 빠른 응답 | `gpt-6-luna` | medium → high (`git_ops` low) | `explorer` · `git_ops` |

- 현재 Codex 실행기에서 프로젝트의 명명 역할은 로드된 역할 정의의 모델·추론을 쓴다. `agent_type="be_executor"`처럼 역할을 지정할 때는
  `model`·`reasoning_effort`를 생략한다. 세션마다 `spawn_agent` 역할 설명에서 고정 여부를 확인한다.
- 호출별 모델·추론 지정이 필요하고 위임 범위가 허용하면 `agent_type="default"`에 `model`·`reasoning_effort`·`fork_turns="none"`을 넘긴다.
  일반 등급 예시는 `spawn_agent(agent_type="default", model="gpt-6.1-terra", reasoning_effort="medium", fork_turns="none", ...)`이다.
  작업 메시지에 적용할 역할 지침, 권한·편집 범위와 검증 방법을 담는다. [Codex 호출 실측](../../../docs/ai-agents.md#codex-병렬-호출-실측)
- 등급 고르기: T0 은 메인 세션 직접, T1(위험 신호 없음)은 일반, T1(신호 1개)·T2 는 핵심. T3 는 구현을 핵심에 추론 한 단계 위
  (돈·동시성이 꼬였거나 원인 미상 버그는 최대), 검토는 핵심 기본에 신호가 걸린 영역 리뷰어(결제·보안·DB)만 한 단계 위.
  ARCHITECTURE 는 설계(서비스 3개 이상·공개 계약 변경·재설계는 최대). 탐색은 빠름, 결제·인증처럼 틀리면 비싼 위치 찾기는 빠름 등급에 `high`.
- 같은 일에서 두 번 실패하고 호출별 지정이 허용되면 추론을 먼저, 그다음 모델을 한 단계 올린다. 최대 추론은 등급 표의 값을 넘기지 않는다.
- 보고에 실제로 쓴 등급·모델·추론 수준을 적는다. 위임할 수 없으면 메인 세션이 같은 순서로 처리한다.
- 위치를 아는 파일 몇 개 읽기, 단일 git 명령은 메인 세션이 직접 한다. 하위 에이전트는 새 컨텍스트로 시작하므로 띄우는 비용이 더 크다.
- `spawn_agent`의 기본 `fork_turns="all"`은 부모 기록 전체를 넘겨 토큰이 늘어난다. 탐색·검토처럼 지시로 충분한 일은 `fork_turns="none"`으로 띄우고
  경로·브랜치·이슈 번호·검증 결과·원하는 출력 형식을 메시지에 모두 담는다.
- 결과는 요약으로 받는다. diff·파일 원문을 통째로 돌려받지 않는다.

## 병렬 실행

순차가 기본이 아니다. 아래 네 패턴에 맞으면 병렬로 돌리고, 금지 조건에 걸리면 순차로 돌린다.
한 번에 띄우는 역할은 보통 2~4개다. 그보다 많으면 합치는 비용이 더 크다.

| 패턴 | 언제 | 어떻게 |
|------|------|--------|
| (a) 탐색 fan-out | 찾을 곳이 서로 독립인 질문이 2개 이상 (서비스별 · 계층별) | `explorer` 여러 개를 **한 턴에서** (`spawn_agent` 를 연달아 호출해) 부른다. 질문마다 범위(서비스 · 패키지)를 좁혀 나눈다 |
| (b) 검토 fan-out | 구현 · 검증이 끝난 diff | 해당 영역 리뷰어(`be-hexagonal-reviewer` · `be-db-reviewer` · `be-security-reviewer` · `be-payment-reviewer` · `fe-reviewer`)와 최종 `reviewer` 를 **한 턴에서** (`spawn_agent` 를 연달아 호출해) 동시에 부르고 메인 세션이 합친다. `reviewer` 를 영역 검토 뒤로 미루지 않는다 |
| (c) 쓰기 병렬 | 파일 · 모듈 소유권이 겹치지 않는 구현이 2개 이상 | 쓰기 역할마다 워크트리를 격리한다 (작업자마다 별도 worktree). 프롬프트에 **소유 경로 목록**을 주고 그 밖은 고치지 않게 한다. 검증은 바꾼 클래스 테스트까지만 시키고 모듈 check 는 생략하게 한다 — 모듈 check 는 합친 뒤 메인 세션이 한 번 |
| (d) 파이프라인 | PR 이 조각(A → B)으로 나뉠 때 | 조각 A 를 **커밋한 뒤** A 의 검토 fan-out 과 조각 B 의 구현을 겹친다. 리뷰어는 A 커밋 범위(`<base>..<A 커밋>`)만 보고, B 는 A 커밋 위에서 만든 격리 워크트리에서 구현한다. B 는 A 의 공개 계약 · 스키마가 확정된 뒤에만 시작하고, A 의 지적이 B 범위에 닿으면 B 를 멈춘다 |

**금지 — 아래면 순차로 돌린다**

- 둘 이상의 쓰기 역할이 함께 건드리는 것: 공개 계약(고객 · 어드민 · internal API, 이벤트 스키마, FE 가 쓰는 DTO), DB 스키마 · DDL,
  도메인 공용 객체(같은 aggregate · 상태 전이 표), `build.gradle` · `settings.gradle` · 공용 core 모듈, `package.json` · lockfile, `backend/docs` 같은 문서 한 파일.
- 같은 서비스 · 같은 컨텍스트의 수직 조각(Controller → UseCase/Facade → Processor → Port → Adapter)을 계층별로 나눠 맡기는 것.
  in-port · out-port 인터페이스와 그 반환 타입(Info · QueryResult)은 한 쓰기 역할이 소유한다. 쓰기 병렬은 서로 다른 서비스나 다른 컨텍스트 단위로만 나눈다.
- 앞 단계 결과가 뒤 단계 입력인 것: 설계 → 구현, 원인 확정 → 수정, 검토 지적 → 반영.
- 같은 PC 에서 Gradle 모듈 check 를 여러 개 동시에 돌리는 것. 검증은 메인 세션이 합친 뒤 한 번 돌린다 (`backend/docs/local-run-guide.md` §4-1).

**합치기 — 쓰기 병렬 뒤 메인 세션이 한다**

1. 각 격리 워크트리의 변경을 확인하고, **소유 경로만** 그 워크트리에서 스테이징 · 커밋한 뒤 작업 브랜치로 `cherry-pick` 한다 (merge 금지).
   `git status --short` 로 untracked 파일을 먼저 보고 **파일 단위로** 스테이징한다 — 디렉터리째 올리면 `.env` · `application-local.yml` 같은 로컬 파일이 딸려 간다.
   소유 경로 밖이 바뀌었으면 받지 않는다.
2. 충돌은 메인 세션이 직접 푼다. 하위 에이전트에 다시 맡기지 않는다.
3. 합친 뒤 바꾼 모듈의 검증을 메인 세션이 다시 돌린다. 각 워크트리의 "통과" 보고는 근거가 아니다.
   검토 fan-out 도 워크트리별이 아니라 **합친 diff** 기준으로 한 번 돌린다 — 경계 위반은 합친 뒤에야 보인다.
4. 임시 브랜치 · 워크트리를 정리한다 (변경 없는 Claude 격리 워크트리는 자동 정리된다).

## 1. CLASSIFY

| 유형 | 대상 |
|------|------|
| `SIMPLE` | 위치와 계약이 분명한 DTO, 매핑, 단순 검증·설정, 작은 테스트, 문구 |
| `FEATURE` | 일반적인 단일 서비스 기능 |
| `BUG` | 원인 분석이 필요한 버그. 상태·트랜잭션·동시성이 얽히면 여기 |
| `REFACTOR` | 동작을 보존하면서 구조를 바꾸는 변경 |
| `ARCHITECTURE` | 서비스 경계·서비스 간 정합성·보안·메시징 설계 |
| `LARGE_FEATURE` | 여러 서비스(또는 BE+FE)에 걸쳐 발견 역할이 둘 이상 필요한 작업 |

## 2. COMPLEXITY

| 등급 | 의미 | 기본 깊이 |
|------|------|-----------|
| `T0` | 위치·계약·검증이 확정된 국소 변경 | 메인 세션이 직접. 탐색·설계·별도 검토 생략 가능 |
| `T1` | 한 모듈 안의 일반 구현·수정 | 구현 역할 + 대상 테스트 |
| `T2` | 여러 계층, 공개 API, 쿼리·인덱스, 경계 검토가 함께 있는 작업 | 구현 + 검토 역할 1~2 |
| `T3` | 실수 비용이 큰 작업 | 설계 고정 + 구현 + 해당 검토 역할 전부 |

`T3` 는 아래 신호 중 **2개 이상**이 작업 범위에 실제로 있을 때다. 하나뿐이면 `T2` 다.

- **결제 (승인·취소·환불·웹훅)**
- **재고 선점·만료처럼 시간과 동시성이 있는 상태**
- 주문·결제 상태 전이 변경
- 멱등성
- 인증·인가 · 어드민 권한
- 개인정보 (주소·전화번호)
- 서비스 간 정합성 (한쪽만 성공하는 경로)
- DB 스키마 변경 · 대량 데이터 이관
- 공개 API 하위 호환 (FE 계약 변경)
- Gateway·security-core 공통 변경
- 장애 원인 미상

## 3. EXPLORE

- `T0` 이거나 수정 위치가 이미 특정되면 생략한다.
- 위치·호출 흐름이 불명확할 때만 `explorer` 를 부른다. 질문과 찾을 범위(서비스·패키지)를 좁혀서 넘긴다.
- 서로 독립인 질문이 둘 이상이면 병렬 실행 (a) 로 나눠 **한 턴에서** (`spawn_agent` 를 연달아 호출해) 부른다.

## 4. PLAN

- `T0`·`T1` 은 메인 세션이 범위와 순서를 짧게 고정한다.
- `T2` 이상은 구현 전에 범위, 보존할 동작, 검증 방법을 고정한다. 새 컨텍스트면 `/backend-feature-bootstrap`.
- `ARCHITECTURE` 와 `T3` 는 `architect` 의 설계가 저장소 증거와 맞을 때만 구현으로 넘긴다.
- `LARGE_FEATURE` 는 백엔드에 `/backend-multi-agent` 를 적용하고, FE 영향은 별도 작업 단위로 정리한다. FE 이슈 등록·담당자 지정은 요청받은 범위에서만 수행한다.

## 5. IMPLEMENT

| 유형 | 구현 |
|------|------|
| `SIMPLE` | 메인 세션이 직접 |
| `FEATURE` · `BUG`(원인 확정 후) · `REFACTOR` | BE는 `be-executor`, FE는 `fe-implementer` 한 명 |
| `ARCHITECTURE` | 구현 요청이 있을 때만, 확정된 계획을 `be-executor` 에게 |

구현 역할의 등급(모델 · 추론)은 `모델 라우팅` 절로 정한다.
공유 파일·공개 계약·DB 스키마·도메인 객체를 고치는 쓰기 역할은 **한 번에 하나만** 실행한다.
소유권이 겹치지 않는 구현이 둘 이상이면 병렬 실행 (c) 의 조건 · 합치기 규칙을 지켜 동시에 돌릴 수 있다.

## 6. VERIFY

대상 범위의 컴파일과 관련 테스트를 **메인 세션이 직접** 돌린다. 하위 에이전트의 "통과했다" 를 완료 근거로 쓰지 않는다.

```bash
cd backend
./gradlew :service:<svc>:cleanTest :service:<svc>:check --no-build-cache   # 바꾼 모듈만(여러 개면 나열)
./gradlew compileTestJava                                                  # core 등 공용 모듈을 바꿨을 때 — 전 모듈 컴파일만
```

- 루트 `./gradlew check`(전 모듈 테스트)는 로컬에서 돌리지 않는다. 다른 모듈은 PR 의 CI(`backend-ci` 그룹 job 건수 표 — 바꾼 모듈과 그 의존 모듈)로 확인한다 — 같은 PC 에서 여러 세션이 빌드한다(`backend/docs/local-run-guide.md` §4-1).
- 데몬을 쓴다. `--no-daemon` 은 JVM 크래시 직후 한 번 다시 돌릴 때만, `./gradlew --stop` 은 쓰지 않는다. 하위 에이전트 프롬프트에도 이 규칙을 넣는다.

FE 변경은 `frontend/`에서 `pnpm lint`, `pnpm format:check`, `pnpm typecheck`, `pnpm test`, `pnpm build`를 실행한다.
문서·AI 설정만 바꾼 경우에는 관련 형식·경로·인코딩 검증을 실행한다.

## 7. REVIEW

| 범위 | 검토 역할 |
|------|-----------|
| 계층·Port/Adapter | `be-hexagonal-reviewer` |
| 엔티티·쿼리·인덱스 | `be-db-reviewer` |
| 인증·인가·어드민·키 | `be-security-reviewer` |
| 결제·주문·재고 | `be-payment-reviewer` |
| 프론트엔드 BFF·쿠키·금액·테마 | `fe-reviewer` |
| 최종 diff 전반 | `reviewer` |

- `T0` 은 대상 테스트로 끝낸다. `T1`·`T2` 는 해당 검토 1~2개, `T3` 는 해당 검토 전부 + `reviewer`.
- 영역 리뷰어와 `reviewer` 는 읽기 전용이라 위임이 허용되고 하위 에이전트를 사용할 수 있으면 **병렬로** 부르고, 그 외에는 메인 세션이 순차 검토한다 (병렬 실행 (b)). `reviewer` 를 영역 검토가 끝난 뒤 따로 부르지 않는다.
- 각 검토 역할에 같은 입력(브랜치 · base · 바꾼 파일 목록 · 설계 결정 · 실행한 검증)을 주고, 자기 영역 밖 지적은 짧게만 남기게 한다. 합칠 때 중복 지적은 하나로 묶는다.
- CRITICAL/HIGH는 해결하고 다시 검증한다. MEDIUM/LOW도 영향과 범위에 따라 수정하거나 남긴 이유를 보고한다.

## 8. SHIP

- 커밋은 메인 세션이 경로를 하나씩 스테이징해 만든다. 커밋이 여러 개이고 경로·메시지가 확정됐으면 `git-ops` 에 넘겨도 된다.
- PR 은 `/pr` 에 **검증 결과를 인자로** 넘겨 만든다.
  예: `/pr 검증: ./gradlew :service:order-service:test 통과 · 참고: payment-guard HIGH 0`
- 머지 후 워크트리·브랜치 정리와 이슈 체크박스 갱신은 PR 번호·완료 항목을 적어 `git-ops` 에 맡긴다.

## 완료 조건

1. 요청한 동작이 구현되었다.
2. 영향 범위가 컴파일되고 관련 테스트가 실제로 돌아 통과했다.
3. 필요한 수준의 검토가 끝났고 CRITICAL/HIGH 지적이 해결되었다.
4. 불필요한 변경과 겹치는 동시 편집이 없다.
5. 보고에 `TYPE`, `COMPLEXITY`(T3 면 해당 신호), 실제 사용한 역할과 등급(`model` · `effort`), 병렬로 돌린 단계, 실행한 검증, 남은 위험이 있다.
